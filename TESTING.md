# Практическое задание №7 — Тестирование работоспособности системы

## Цель

Проверить, что ML-сервис работает как единая система и корректно выполняет основные пользовательские и бизнес-сценарии.

Тестирование охватывает:

- REST API;
- бизнес-логику;
- PostgreSQL;
- RabbitMQ;
- ML-воркеры;
- баланс и транзакции;
- историю ML-запросов;
- пакетную обработку частично валидных данных.

## Подход к тестированию

Для автоматического тестирования используется `pytest`.

Тесты разделены на отдельные функции `test_*`. Поэтому ошибка в одном сценарии не останавливает выполнение остальных тестов: pytest выполняет их независимо и показывает отдельный результат для каждого.

Для подготовки состояния используются pytest fixtures.

Основные fixtures:

- `registered_user` — создаёт нового пользователя;
- `funded_user` — создаёт пользователя и пополняет его баланс на `10.00`;
- `batch_funded_user` — создаёт пользователя с балансом `20.00`;
- `completed_prediction` — создаёт подготовленного пользователя, отправляет ML-задачу и ожидает её завершения.

Для каждого теста создаётся новый пользователь с уникальным логином. Поэтому тесты не используют результаты предыдущих тестов.

Например, тест истории транзакций не зависит от теста успешного предсказания. Fixture самостоятельно:

```text
создаёт пользователя
→ пополняет баланс
→ отправляет ML-запрос
→ ждёт завершения задачи
→ передаёт подготовленные данные тесту
```

## Тестируемая архитектура

```text
REST client
    ↓
  Nginx
    ↓
 FastAPI
    ↓
PostgreSQL

ML-запрос:
FastAPI
    ↓
RabbitMQ
  ↙       ↘
worker-1  worker-2
    ↓
ML-модель
    ↓
FastAPI
    ↓
PostgreSQL
```

ML-тесты проверяют не только HTTP-ответ FastAPI, но и полный асинхронный сценарий через RabbitMQ и worker.

## 1. Пользователи

Проверяются:

- регистрация нового пользователя;
- успешная авторизация;
- повторная авторизация;
- неверный пароль;
- повторная регистрация;
- доступ к защищённому endpoint без авторизации.

Каждый тест создаёт собственного пользователя через fixture или вспомогательную функцию.

Это исключает зависимость от порядка запуска тестов.

## 2. Баланс

Проверяется начальный баланс нового пользователя:

```text
0.00
```

Также проверяются:

- успешное пополнение на `10.00`;
- изменение баланса после пополнения;
- запрет отрицательного пополнения;
- отсутствие изменения баланса после ошибочного пополнения.

## 3. Ошибочные ML-запросы

Fixture `funded_user` создаёт пользователя с балансом:

```text
10.00
```

После этого отдельно проверяются:

### Неизвестная модель

```text
POST /predict
→ HTTP 400
→ баланс остаётся 10.00
```

### Пустой текст

```text
POST /predict
→ HTTP 422
→ баланс остаётся 10.00
```

Таким образом подтверждается, что ошибочный ML-запрос не приводит к списанию средств.

## 4. Успешный ML-запрос

Fixture `completed_prediction` выполняет полный сценарий:

```text
новый пользователь
→ баланс 10.00
→ POST /predict
→ HTTP 202
→ RabbitMQ
→ worker
→ ML-модель
→ completed
```

Тест проверяет:

- статус `completed`;
- наличие результата предсказания;
- наличие `worker_id`;
- списание `10.00`;
- итоговый баланс `0.00`.

Таким образом проверяется интеграция REST API, RabbitMQ, ML-worker, ML-модели, PostgreSQL и бизнес-логики списания.

## 5. Недостаточный баланс

Для нового пользователя с балансом `0.00` выполняется ML-запрос.

Ожидается:

```text
HTTP 402
```

После отказа баланс остаётся:

```text
0.00
```

## 6. История транзакций

Тест `test_transaction_history` получает собственный подготовленный сценарий через fixture `completed_prediction`.

Для этого пользователя создаются:

```text
1 credit — пополнение 10.00
1 debit — списание 10.00 за ML-задачу
```

Проверяется:

- наличие credit-транзакции;
- наличие debit-транзакции;
- сумма операций;
- соответствие `task_id` debit-транзакции завершённой ML-задаче.

Тест не зависит от других тестов истории, баланса или предсказаний.

## 7. История ML-запросов

Тест `test_prediction_history` также получает собственную завершённую ML-задачу через fixture.

Проверяется:

- наличие нужного `task_id` в истории;
- статус `completed`;
- сохранённый результат;
- списанная сумма.

## 8. Частично валидные batch-данные

Fixture `batch_funded_user` создаёт нового пользователя с балансом:

```text
20.00
```

В backend отправляется пакет:

```json
{
  "model_name": "sentiment-model",
  "rows": [
    "Мне очень нравится этот сервис",
    "",
    123,
    "Это ужасный продукт"
  ]
}
```

Ожидается:

```text
строка 1 → valid
строка 2 → invalid
строка 3 → invalid
строка 4 → valid
```

Backend принимает две корректные строки и возвращает две ошибочные строки отдельно.

Для двух принятых строк создаются ML-задачи. Тест ожидает их завершения и проверяет списание:

```text
10.00 + 10.00
```

Итоговый баланс:

```text
0.00
```

Таким образом подтверждается, что ошибочные строки не оплачиваются.

## 9. Batch при недостаточном балансе

Для нового пользователя с балансом `0.00` отправляются две корректные строки.

Ожидаемый результат:

```text
HTTP 402
```

Баланс остаётся `0.00`.

## Независимость тестов

Главное изменение относительно первоначальной версии тестирования — отказ от одного большого последовательного `run_tests()`.

Ранее сценарии выполнялись внутри одной функции:

```text
регистрация
→ баланс
→ prediction
→ история
→ batch
```

Если один `assert` завершался ошибкой, выполнение оставшихся сценариев прекращалось.

В текущей реализации каждый сценарий оформлен отдельной функцией:

```python
def test_login(...):
    ...

def test_topup(...):
    ...

def test_successful_prediction(...):
    ...
```

Pytest выполняет их независимо.

Fixtures используются только для подготовки необходимого начального состояния конкретного теста. Они не передают данные между разными тестами.
